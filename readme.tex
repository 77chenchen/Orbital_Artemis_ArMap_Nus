\section*{Motivation}
\addcontentsline{toc}{section}{Motivation}

Navigating through the NUS campus can be difficult because complete geospatial and indoor facility data is not always publicly available or intuitive to use. Even after reaching the correct building, students may still need to locate lecture rooms, tutorial classrooms, study spaces, restrooms, lifts, printing services, and other facilities.

These navigation needs are closely tied to students' daily routines and schedules. Atlas is motivated by the need for a smarter, more context-aware campus assistant that supports both outdoor movement across NUS and indoor discovery within selected buildings.

\section*{Our Aim}
\addcontentsline{toc}{section}{Our Aim}

Atlas aims to create a seamless campus assistant for NUS students. The project combines map-based navigation, facility discovery, schedule-aware guidance, and a daily assistant interface so that students can move through campus more confidently.

For Milestone 01, our goal is to establish a working full-stack prototype: authentication, a protected dashboard, campus data APIs, map rendering, location search, and deployment. Later milestones will extend this foundation toward richer AR-style navigation, indoor guidance, and smarter route planning.

\section*{User Stories}
\addcontentsline{toc}{section}{User Stories}

\begin{enumerate}[leftmargin=*]
    \item As an NUS student, I can use the AR map to navigate from my current location to the correct building and classroom so that I can arrive at class on time.
    \item As an NUS student unfamiliar with a campus building, I can locate indoor facilities such as restrooms, lifts, study spaces, and printing services so that I can navigate the building more easily.
    \item As an NUS student, I can receive location-aware reminders and suggestions based on my schedule and current position so that I can manage my day more smoothly.
    \item As a freshman unfamiliar with NUS, I can search for lecture theatres, tutorial rooms, and laboratories so that I can navigate the campus confidently.
    \item As an exchange student visiting NUS for the first time, I can follow AR navigation instructions instead of static maps so that navigation feels more intuitive.
    \item As a student rushing between consecutive classes, I can estimate travel time between buildings so that I know when to leave for class.
    \item As a student studying late on campus, I can locate nearby study spaces and facilities through AR guidance so that I can find suitable places quickly.
    \item As a wheelchair user, I can find wheelchair-friendly routes, accessible entrances, and lifts so that I can travel across campus more comfortably.
    \item As a student unfamiliar with NUS bus routes, I can locate nearby shuttle bus stops and view available shuttle services so that I can travel more efficiently.
    \item As a student attending events on campus, I can receive recommendations for nearby ongoing events and activities so that I can participate more conveniently.
    \item As a student looking for a quiet place to study, I can receive recommendations for less crowded study areas and facilities so that I can study more effectively.
    \item As a student entering a large building for the first time, I can receive indoor AR guidance to classrooms, offices, and facilities so that I do not need to rely on physical signboards.
    \item As a student who frequently prints documents on campus, I can quickly locate nearby printing services so that I can save time.
    \item As a student concerned about safety, I can locate emergency exits, first-aid points, and security offices within campus buildings so that I can respond quickly during emergencies.
    \item As a student contributing to the campus community, I can add or update map information such as facilities, pathways, and corrections so that the map remains accurate and useful.
    \item As a student with back-to-back classes, I can receive reminders on when to leave my current location so that I can arrive on time for my next lesson.
    \item As a visitor attending an event at NUS, I can navigate to specific venues and facilities so that I can find locations without prior knowledge of the campus layout.
    \item As a student using the system daily, I can save frequently visited locations so that I can access navigation more quickly.
    \item As a student who wants to avoid crowded routes, I can view alternative paths and facility options so that I can choose a route that matches my comfort and time constraints.
    \item As a campus administrator maintaining navigation data, I can review user-submitted map corrections before they are published so that the system remains accurate and trustworthy.
\end{enumerate}

\section*{Project-Level Software Engineering}
\addcontentsline{toc}{section}{Project-Level Software Engineering}

Atlas applies software engineering practices at the project level, not only inside individual files. The goal is to make the project trackable, reviewable, testable, and deployable throughout Orbital.

\subsection*{GitHub Project Management}
\addcontentsline{toc}{subsection}{GitHub Project Management}

GitHub issues are used as the team progress log. Each issue represents a concrete feature, defect, or engineering task, such as authentication, protected routing, map rendering, mobile layout, dashboard integration, and map polygon fixes. The public issue tracker functions as both a task board and an audit trail for mentor review.

The intended workflow is:

\begin{enumerate}[leftmargin=*]
    \item Break milestone requirements into GitHub issues with clear acceptance criteria.
    \item Assign work to a team member and connect it to the relevant feature area.
    \item Implement changes on a focused branch instead of mixing unrelated work.
    \item Review the change through a pull request before merging to \texttt{main}.
    \item Use the issue and pull request history as progress logs for milestone submission.
\end{enumerate}

This workflow is intentionally heavier than a quick prototype workflow. It is justified because Artemis projects are expected to demonstrate consistent engineering discipline and maintainability, not only visible screens.

\section*{Authentication and Protected Access}
\addcontentsline{toc}{section}{Authentication and Protected Access}

Authentication allows students to enter Atlas through email/password login, registration, demo mode, or Google Sign-In. Once authenticated, users can access protected pages such as the dashboard and map.

\subsection*{Email, Demo, and Google Sign-In}
\addcontentsline{toc}{subsection}{Email, Demo, and Google Sign-In}

The login system supports multiple entry paths. Email/password login provides a traditional account flow, demo mode allows quick testing without setup, and Google Sign-In supports a more realistic student login experience.

\screenimage{Authentication Screen}{readme_assets/authentication-login-page.png}{0.96}

On the backend, Atlas verifies credentials and issues a JWT. For Google Sign-In, the frontend obtains a Google ID token and sends it to the backend, where it is verified against the configured Google client ID. If verification succeeds, the backend returns the same application JWT format used by email login. This keeps the rest of the application independent of the authentication method.

From a software engineering perspective, this follows separation of concerns. The frontend handles user interaction and token storage, while the backend performs trust-sensitive verification and token signing. This is safer than trusting the frontend alone, because the backend remains the authority for protected access. The trade-off is that local development requires OAuth configuration and network access to Google's verification service, but the design is closer to a production-ready authentication system.

\subsection*{Protected Routes}
\addcontentsline{toc}{subsection}{Protected Routes}

Protected routes guard the dashboard and map pages. If a user is not authenticated, the frontend redirects them to the login screen. API requests also attach the JWT in the \texttt{Authorization} header, allowing the backend to reject unauthenticated access consistently.

This pattern reduces duplicated access checks. Instead of manually checking login state inside every page component, protected routing creates a reusable access boundary. It also makes later feature additions easier, because new protected pages can reuse the same wrapper.

\section*{Campus Map Rendering}
\addcontentsline{toc}{section}{Campus Map Rendering}

The map feature gives users an interactive visual interface for campus navigation. For Milestone 01, Atlas renders a MapLibre/OpenStreetMap-based campus map centered around NUS and prepares the map surface for future AR and indoor navigation work.

\subsection*{MapLibre and OSM Tiles}
\addcontentsline{toc}{subsection}{MapLibre and OSM Tiles}

The frontend uses MapLibre to render map tiles and manage markers, routes, and future geospatial overlays. This gives the project an open-source map engine that can be extended with custom campus data instead of relying only on a closed map UI.

\screenimage{Campus Map Screen}{readme_assets/campus-map-screen.png}{0.96}

The map logic is separated into a map initialization module, a \texttt{MapEngine} helper, routing services, and UI components. This modular approach prevents the main map page from becoming a single large component. It also makes it easier to add bus layers, indoor facility overlays, or AR-style markers later.

The bug tracked in issue \#17 showed why this separation matters. Rendering geospatial polygons and map layers can fail due to data format mismatches, layer ordering, or source initialization timing. By separating map engine actions from UI state, Atlas can debug and update rendering logic without changing authentication or dashboard code.

\subsection*{Route Tracing}
\addcontentsline{toc}{subsection}{Route Tracing}

Route tracing allows selected start and end points to be drawn on the map. In Milestone 01, this is implemented as a route line on the MapLibre layer. It is an early prototype of the proposal's broader navigation goal.

The engineering trade-off is that route tracing is currently web-map based rather than full AR. This is intentional for Milestone 01: a reliable map and routing foundation reduces risk before adding heavier AR components in later milestones.

\section*{Daily Assistant, Facilities, and Schedule}
\addcontentsline{toc}{section}{Daily Assistant, Facilities, and Schedule}

The daily assistant dashboard connects campus navigation to student routines. Instead of treating the map as a standalone feature, Atlas combines schedule items, next-location context, building data, facility filters, and recommendation cards into one student-facing workflow.

\subsection*{Facility Discovery}
\addcontentsline{toc}{subsection}{Facility Discovery}

Facility discovery focuses on practical indoor and near-indoor needs: study areas, lifts, restrooms, and printing locations. In Milestone 01, the backend seeds representative NUS building and facility data in SQLite and exposes it through protected API endpoints.

\begin{center}
\renewcommand{\arraystretch}{1.35}
\begin{tabularx}{\textwidth}{|L{0.28\textwidth}|X|}
\hline
\textbf{Endpoint / Data} & \textbf{Purpose} \\
\hline
\texttt{GET /api/buildings} & Returns campus buildings with code, name, description, coordinates, floor count, and indoor support status. \\
\hline
\texttt{GET /api/facilities} & Returns facilities and supports filters such as \texttt{building=COM1} and \texttt{type=study\_space}. \\
\hline
Seeded demo data & Allows evaluators to test building and facility discovery without requiring private production data. \\
\hline
\end{tabularx}
\end{center}

The main design decision is to model facilities separately from buildings. This allows Atlas to add many facility records under one building and later attach richer indoor information such as floor plans, accessibility paths, or AR markers.

\subsection*{Schedule Management}
\addcontentsline{toc}{subsection}{Schedule Management}

Schedule management is included because a campus assistant becomes more useful when it understands where the student needs to go next. The current prototype supports viewing, creating, and deleting schedule items. Each item can include a location code, allowing recommendation cards to connect time-based context with campus data.

This feature also prepares the app for future NUSMods integration. Rather than hard-coding a static timetable into the frontend, the backend exposes schedule APIs and stores schedule data in SQLite. This gives the team a stable place to add timetable sync, conflict warnings, and route preparation in later milestones.

\subsection*{Recommendation Cards}
\addcontentsline{toc}{subsection}{Recommendation Cards}

Recommendation cards summarize useful actions such as where the next class is, which building context matters now, or which facilities are likely relevant. In M1, the recommendations are intentionally simple and explainable. This helps the team test the user workflow before adding more advanced ranking or personalization.

\subsection*{Bus and Transit Context}
\addcontentsline{toc}{subsection}{Bus and Transit Context}

Campus movement often involves a choice between walking, waiting for a shuttle, or combining both. Atlas therefore includes bus context as an Artemis extension feature. The backend supports endpoints for bus stops, routes, arrivals, active vehicles, alerts, and context near a latitude/longitude point.

The current design keeps bus data server-side. This avoids exposing private API keys in the browser and allows the backend to cache, normalize, or fall back to demo data. For M1, this establishes the integration boundary even if later milestones refine the frontend presentation and multimodal routing logic.

\section*{CI/CD Pipeline}
\addcontentsline{toc}{section}{CI/CD Pipeline}

The CI/CD pipeline is designed around GitHub as the source of truth and Render/Docker as the deployment path. Its purpose is to prevent unverified changes from reaching production and to make deployment reproducible.

\subsection*{Continuous Integration Gates}
\addcontentsline{toc}{subsection}{Continuous Integration Gates}

For pull requests and pushes to \texttt{main}, the intended GitHub Actions workflow runs the following jobs:

\begin{enumerate}[leftmargin=*]
    \item Checkout repository.
    \item Install frontend dependencies with \texttt{npm ci}.
    \item Build frontend with \texttt{npm run build}.
    \item Install backend dependencies through Go modules.
    \item Run backend checks with \texttt{go test ./...}.
    \item Build the production Docker image.
\end{enumerate}

The corresponding workflow structure is:

    \centering
    \fbox{

            jobs:\\
            \hspace*{1em}frontend-build: npm ci + npm run build\\
            \hspace*{1em}backend-test: go test ./...\\
            \hspace*{1em}docker-build: docker build .
            }
            \vspace{0.4em}
        \end{minipage}
    }
    \caption*{CI workflow gates for pull requests and main branch updates}
\end{figure}

\subsection*{Continuous Deployment Path}
\addcontentsline{toc}{subsection}{Continuous Deployment Path}

Atlas currently uses a production deployment path built from the repository's \texttt{Dockerfile}, \texttt{docker-compose.yml}, Caddy configuration, and Render-hosted application URL. The deployment flow is:

\begin{enumerate}[leftmargin=*]
    \item Merge reviewed changes into \texttt{main}.
    \item Build the frontend with Vite.
    \item Build the Go backend binary.
    \item Package the production app through the multi-stage Dockerfile.
    \item Serve the app over HTTPS through the configured deployment host.
    \item Validate the deployed app using the manual test matrix and video walkthrough flow.
\end{enumerate}

Environment variables such as \texttt{JWT\_SECRET}, \texttt{GOOGLE\_CLIENT\_ID}, \texttt{DB\_PATH}, \texttt{ALLOWED\_ORIGIN}, and bus API credentials are kept outside source code. This keeps deployment configurable while avoiding accidental exposure of private credentials.
